## ADR-020 — SDK v2 `createMcpHandler` as the MCP serving entry
**Status:** Accepted  
The installed SDK is MCP TypeScript SDK v2 (`@modelcontextprotocol/server` 2.4.0), which ships `createMcpHandler`: one entry serving both the 2025 `initialize` handshake and the 2026-07-28 `server/discover` era. We use it instead of hand-wiring a `WebStandardStreamableHTTPServerTransport` per request. Consequences:
- Serving is **stateless per HTTP exchange**; `McpServer` instances are constructed per exchange by a factory and never shared. There is no server-side session store yet, so a client-supplied `mcp-session-id` carries no authority and is ignored.
- On that stateless legacy leg the SDK answers `GET`/`DELETE` with `405`, so MCP session resumption and server→client notifications are not available until Phase 7 introduces session tracking.
- `HOST` is restricted to loopback values so the binding cannot drift from the DNS-rebinding allowlist.

## ADR-021 — Rejecting the Hono JSON body middleware
**Status:** Accepted  
`createMcpHonoApp` pre-parses JSON bodies and answers malformed input with a plain-text `400 Invalid JSON`. The MCP endpoint instead hands the raw `Request` to the handler so malformed bodies produce a JSON-RPC `-32700` parse error and oversize bodies a `413` — the behavior an MCP client can actually interpret. Host/Origin middleware is still applied explicitly, per SDK guidance that transport-level DNS-rebinding protection is deprecated in favour of middleware.

## ADR-022 — No workspace split yet; module layout as the seam
**Status:** Superseded 2026-11-23 by the repository restructuring: the gateway moved into `apps/gateway` as a workspace package (`@universal-mcp-gateway/gateway`), the root manifest became a thin orchestration layer, and the lockfile re-mapping was verified to keep every dependency resolution identical. `packages/shared` and `packages/config` remain deferred — no code is shared by the two apps, so there is still nothing to put in them. The original decision text below describes the Phase 2 layout as it was.  
The target architecture is a pnpm workspace (`apps/gateway`, `packages/shared`, `packages/config`). Phase 2 keeps a single package with an intentional module layout instead: `src/domain` (schemas, entities, repository interfaces), `src/shared` (error taxonomy), `src/config`, `src/core`, `src/infrastructure`. Reasons:
- `packages/shared` would have exactly one consumer until the dashboard exists (Phase 9). A package with one importer buys a build step and a version to keep in sync, not isolation.
- Moving `src/` requires a workspace reinstall, which re-resolves the native `better-sqlite3` build. That risk is not worth taking to relocate files that have no second consumer.
- The directory boundaries are already the package boundaries. Lifting `src/domain` + `src/shared` into `packages/shared` later is a move plus an import rewrite, with no redesign.
Revisit when the dashboard needs the domain contracts, or when a second runnable app exists.

## ADR-023 — Error taxonomy with one boundary-crossing error type
**Status:** Accepted  
`AppError` is the only error type permitted across a trust boundary. It carries a stable `ErrorCode` (never renamed; the dashboard and clients may branch on it), a client-safe message, log-only `details`/`cause`, and an optional `requestId`. Each code has a fixed category, HTTP status, and JSON-RPC code, so mapping is a table lookup rather than per-handler judgement.
- `toAppError()` collapses everything else into `INTERNAL_ERROR` with a generic message, preserving the original as `cause`. This is what stops SQLite text, filesystem paths, and stack traces from reaching a client.
- `describeErrorForLog()` is the log-only view: cause chain and stack, never serialized outward.
- Code strings are chosen to match the documented API envelope (`docs/BACKEND_SPEC.md`).

## ADR-024 — Tombstones for backends and agents, hard delete for policies
**Status:** Accepted  
Backends and agents are soft-deleted (`deleted_at`). Activity and audit history reference them, so a hard delete would either orphan or require `SET NULL` — losing "which backend was this?" forever. A tombstone keeps history resolvable and makes "was this ever configured?" answerable. A partial unique index (`WHERE deleted_at IS NULL`) still allows the name to be reused.
- Policies are hard-deleted, with assignments cascading. Nothing historic references a policy id: audit rows store `target_id` as a plain string plus a metadata snapshot, so the trail stays readable.
- Credentials and sessions are never deleted at all. Revocation is a timestamp, and the first revocation wins so the trail cannot silently move.
- Trade-off: tombstoned rows accumulate. A bounded, observable purge is a later operational concern, not a silent cascade.

## ADR-025 — Derived status instead of stored status columns
**Status:** Accepted  
`agent_credentials` and `sessions` have no `status` column. Status is computed from `revoked_at` / `expires_at` against the current time, with revocation winning over expiry. A stored status column can disagree with the timestamps after any partial update or clock-driven transition, and the disagreement is invisible. Deriving it makes that class of bug unrepresentable.
- `backend_runtime.status` *is* stored: it reflects an observed connection state that no timestamp can reconstruct, and it is written by the adapter that owns the connection.

## ADR-026 — Env-only configuration, no YAML in Phase 2
**Status:** Accepted  
Configuration comes from environment variables with documented defaults; YAML is not read. Nothing in this phase needs a nested shape, and a second source adds a precedence rule to implement, document, and test without buying anything. Precedence is strict and one-directional: explicit overrides → environment → defaults.
- `parseConfig()` is pure: it never exits, logs, or throws. `loadConfig()` throws `ConfigError`; only the process entry decides to exit. This is what makes configuration unit-testable.
- `HOST` is restricted to loopback values. Network exposure is a security decision requiring approval and review, not a config toggle.
- Secret *references* require an explicit `secret:` or `env:` scheme. No regex can distinguish a pasted secret (`sk-live-...`) from a variable name (`api-key`), so the scheme makes intent explicit and rejects literals by construction.

## ADR-027 — Validate a proposed config at `POST /backends/validate`, not `:backendId/validate`
**Status:** Accepted  
`docs/BACKEND_SPEC.md` originally listed `POST /api/v1/backends/:backendId/validate`. Validation is useful *before* creation — the dashboard validates a form before saving — and a proposed configuration has no persisted entity, so a path segment addressing one does not exist yet. Requiring a saved backend first would force operators to persist configuration they are still editing.
- The route is declared before `/:backendId`, so the literal `validate` is never parsed as a UUID.
- The response is a validation result with `200` (`{ valid, transport?, normalized?, errors? }`), not a `400`: the request was well-formed and the answer is "this configuration is invalid".
- Trade-off: an id-suffixed form would let an operator re-validate *stored* configuration. That arrives with the Phase 4 adapter, where real connection metadata exists to validate.

## ADR-028 — Optimistic concurrency on backend updates via a `version` column
**Status:** Accepted  
Two admins, or one double-clicked Save, read the same backend and write conflicting edits. Last-write-wins silently discards the other change, which is indistinguishable from success.
- `backends.version` (migration `0002`) is incremented by every persisted update. Update/enable/disable accept an optional `?expectedVersion=`, which turns the write into a single `UPDATE ... WHERE id = ? AND version = ?`. The check and the write are one statement, so no writer can interleave.
- A stale version yields `409 RESOURCE_CONFLICT`; the first writer's data is untouched.
- Omitting `expectedVersion` keeps last-write-wins, which is the sane default for scripts and single-operator use. Requiring it would break every simple `curl`.
- Trade-off: a client must round-trip the version it read. The list and detail responses include it, so this costs nothing beyond not discarding it.

## ADR-029 — Split REST and MCP Host/Origin guards; share the validators
**Status:** Accepted  
`hostHeaderValidation`/`originValidation` from `@modelcontextprotocol/hono` answer `403` with a JSON-RPC envelope. That is correct for `/mcp`: an MCP client parses JSON-RPC and would choke on a REST error body. It is wrong for `/api/v1`: a REST client parses `{ error: { code, message, requestId } }` and would see an unparseable 403.
- The SDK middlewares are scoped to non-API paths. The management API applies `validateHostHeader`/`validateOriginHeader` — the same allowlist logic, imported directly from `@modelcontextprotocol/server` — and formats the result in its own envelope.
- Security logic is therefore not duplicated: one implementation of the loopback allowlist, two response shapes.
- Trade-off: the app has two guard chains, so a future change to the allowlist must be applied via the SDK, not by editing one middleware. Keyword handlers (`app.use` with a path test) keep the split in one file (`apps/gateway/src/core/gateway.ts`) rather than scattering it.

## ADR-030 — The management API is unauthenticated and loopback-only in Phase 3
**Status:** Accepted (interim)  
The API can create, modify, and delete backend definitions but has no authentication. Pretending otherwise would be worse than documenting it.
- What exists: loopback socket check, configured-`HOST` check, `Host` and `Origin` validation, JSON content-type requirement, size limits, strict Zod validation, parameterized SQL, and a non-leaking error envelope. These stop remote and cross-origin misuse.
- What does not exist: identity, per-caller authorization, rate limiting, CSRF tokens. Any local process can call the API.
- Audit rows record `{ type: "admin", id: "local-operator" }` rather than an anonymous actor, so Phase 3 history does not later read as system-generated.
- Revisit in Phase 6 (ADR planned then): dashboard auth, agent credentials, and default-deny authorization. Until then no non-loopback exposure, per `docs/SECURITY.md` release gate.
- **Updated in Phase 6:** agent credentials and default-deny authorization exist, but **for the MCP surface only**. This ADR still describes the management API exactly as it is — unauthenticated and loopback-only — and that API can now mint an agent credential, which makes the boundary more consequential, not less. `GET /api/v1/system` now reports `capabilities.authentication: true` (the MCP surface can verify) plus a live `authentication: required | unavailable` field. See ADR-039.

## ADR-031 — Validation messages echo only field names the gateway defines
**Status:** Accepted  
Error messages must help a caller fix a request without ever repeating what they sent. The naive version — "path and message, not the value" — is insufficient, because Zod puts caller-controlled *keys* into the path and into `unrecognized_keys` messages. A secret pasted into an env-var name (`{"env": {"sk-live-...": "x"}}`) or an unknown top-level field therefore reached the response and the audit log in testing.
- `safeIssuePath()` emits a segment only when it is in `KNOWN_FIELDS`, a literal set of the gateway's own field names. Everything else becomes `(redacted)`.
- `safeIssueMessage()` rewrites `unrecognized_keys` to a count, dropping the names entirely.
- A "looks like an identifier" regex was tried and rejected: `sk-live-ABCDEFGHIJKLMNOP` matches it, so the check cannot distinguish a secret from an env-var name.
- Two name positions are additionally constrained at the schema, which settles most of this by construction: env keys must be POSIX variables (`^[A-Za-z_][A-Za-z0-9_]{0,127}$`, so no hyphens) and header keys must be RFC 7230 tokens.
- Accepted limit: a header *name* that looks like a secret is a legal header name, and header names must be displayed for the config to be legible. It is treated as caller-supplied text (same class as `description`), not as a credential. Attempting to redact it would hide legitimate names like `X-Api-Key`.
- Trade-off: adding a schema field without adding it to `KNOWN_FIELDS` makes its name appear as `(redacted)` in error text. That is cosmetic and fails safe. Both `apps/gateway/tests/api.test.ts` and `apps/gateway/tests/backend-service.test.ts` assert a pasted-key secret never appears in a response or in `audit_events`.

## ADR-032 — Outbound destination policy before the socket, enforced per request
**Status:** Accepted  
Phase 4 makes the gateway dial operator-supplied URLs, which is an SSRF primitive unless destinations are constrained. A definition containing `http://169.254.169.254/` would otherwise turn the loopback-only API into a network scanner.
- Order: scheme (`http`/`https` only) → embedded credentials refused → hostname **resolved** → every returned address classified. String matching is insufficient: `metadata.google.internal` looks public.
- Checked inside the `fetch` the transport uses, not once at connect, so every request and every redirect hop is covered. `redirectPolicy: 'same-origin'` keeps a redirect from reaching a destination that was never checked.
- `ALLOW_PRIVATE_NETWORK=true` opens **only** loopback, RFC 1918, and CGNAT. Link-local (`169.254/16`, `fe80::/10`), unspecified, multicast, and reserved stay refused. This was tightened after a live test showed the original single-list implementation let `169.254.169.254` through when the flag was set — the opt-in exists for local fixtures, not as a general bypass.
- Rejected alternative: a per-backend egress allowlist. Premature — there is no policy engine until Phase 6, and an allowlist with one operator would encode the same host every time.
- **Accepted limit:** check-then-connect leaves a DNS-rebinding window between our lookup and the socket. Closing it needs a custom dialing agent that connects to the resolved IP; the remaining exposure requires a hostile DNS server for a hostname the operator chose themselves.
- TLS verification is never disabled anywhere: no `rejectUnauthorized: false`, no `NODE_TLS_REJECT_UNAUTHORIZED`, no custom agent.

## ADR-033 — One lifecycle manager per process, explicit connect only
**Status:** Accepted  
`apps/gateway/src/adapters/lifecycle.ts` is constructed once in `createGateway()` and shared by the connect routes, the runtime reads, startup recovery, and shutdown. Duplicating it per request would give two views of "is this backend connected", and the second one would be wrong.
- The service layer stays synchronous and connection-free; the manager is the sole owner of processes and HTTP clients. Live objects never enter SQLite.
- **Nothing connects implicitly.** Create, update, and `enable` reconcile runtime state but never dial. A connection needs an explicit `POST /backends/:id/connect`. Before this phase the worst a local caller could do was edit rows; now it can spawn a process, so implicit dialling would widen the blast radius for no benefit.
- One promise chain per backend serializes concurrent connects, so a double-click cannot spawn two children.
- Retry: bounded exponential backoff with ± jitter, transient-only (`BACKEND_TIMEOUT`, `BACKEND_UNAVAILABLE`), off by default. A bad executable, a policy refusal, or rejected credentials is permanent — retrying cannot change the answer.
- Shutdown is sequenced inside `Gateway.close()`: MCP handler → lifecycle → store. A store closed under a running teardown could not persist a truthful row.
- **Accepted limit:** no health probing yet, so `unhealthy` is a legal state nothing sets in Phase 4. Adding a probe without tool discovery would be a timer that only proves the process is alive.

## ADR-034 — Startup recovery rewrites live state; `reconcile` after commit
**Status:** Accepted  
Two related choices about who decides what a change means for a live connection.
- **Recovery distrusts the database.** A persisted `connected` is a claim by a process that no longer exists. `recover()` rewrites `connected`/`connecting`/`unhealthy`/`disconnecting` to `disconnected` (or `disabled` when the config says so), resets `reconnectAttempts`, preserves `lastConnectedAt` as history, and **does not reconnect**. Trusting the row would either lie to the operator or auto-dial on boot — both unacceptable. A persisted `error` is preserved: it is still true.
- **One `reconcile()` per mutation, after the transaction commits.** Each mutating route calls `lifecycle.reconcile(id)` once; the manager re-reads the committed row, compares a connection fingerprint (`connection`, `timeoutMs`, `enabled`), and tears down a live connection whose fingerprint changed. The alternative — five change detectors, one per field — duplicates knowledge of the domain in the route layer and drifts. The manager is the only place that knows what a connection depends on.
- Fingerprint comparison, not a dirty flag: a `PATCH` that changes only `description` leaves the connection alone, which a flag would get wrong.
- Rejected alternative: an event bus between the service and the manager. One process, one caller, no fan-out — an emitter would add ordering questions with nothing to answer them.

## ADR-035 — A `disconnecting` state, added by a table rebuild
**Status:** Accepted  
Teardown is not instantaneous: a child gets stdin end → SIGTERM → grace → SIGKILL. Reporting `connected` while a process is being killed is a lie, and reporting `disconnected` before it exits is worse — the next connect could race the old child.
- `backend_runtime.status` gains `disconnecting` (migration `0003`). SQLite cannot alter a `CHECK`, so the migration rebuilds the table and copies every row inside the runner's transaction.
- The transition set is declared as data (`BACKEND_TRANSITIONS`) and enforced in `persist()`; an illegal edge throws `INTERNAL_ERROR` rather than storing an impossible status. This catches manager bugs at the write instead of at a later read.
- `disconnecting` is transient and never survives a restart: recovery treats it as dead-process state like `connected`.
- **Accepted limit:** the status is only as truthful as the last write. A `SIGKILL` of the gateway itself leaves whatever was last persisted; recovery exists precisely because that cannot be avoided.

## ADR-036 — Namespacing is total, deterministic, and identity-derived
**Status:** Accepted  
`publicToolName(backendId, originalName)` = two normalized segments joined by `__`.
- Normalization replaces **every** character outside `[A-Za-z0-9._-]` with `_`. Total rather than permissive, so a name that survives is always safe to put in a JSON-RPC message, a log line, and a URL path segment, and so two originals that differ only in punctuation (`search items`, `search_items`) become the *same* public name and are therefore caught by collision detection instead of quietly aliasing.
- Names over 128 characters are cut and suffixed with `__<8 hex of SHA-256(backendId, NUL, originalName)>`. The suffix comes from identity, not randomness: the same tool keeps the same public name across restarts and rediscoveries, so a persisted agent config or a client's cached tool list stays valid.
- Rejected alternative: appending a counter or UUID to every name. It would make collisions impossible to *detect*, which hides the real problem — two backends claiming one name — and it breaks the "same name every time" property above.
- Rejected alternative: permissive normalization that preserves the original characters. It would push escaping into every consumer and still allow collisions to differ only by a character no downstream system can represent.
- **Accepted limit:** normalization is lossy, so two genuinely different tools can collapse onto one public name. That is reported, not hidden: the catalog withholds both claimants.

## ADR-037 — Forward the backend's JSON Schema; validate with AJV; never rebuild it in Zod
**Status:** Accepted  
A backend's `inputSchema` is carried as an opaque `Record<string, unknown>` from `tools/list` to the wire, and compiled for argument checking with `fromJsonSchema`.
- Rebuilding each remote schema in Zod would lose `$defs`, `$ref` chains, formats, `additionalProperties`, and vendor extensions — and a gateway that loses schema detail silently weakens the backend's contract. Zod reconstructs the gateway's own contracts; it is the wrong tool for forwarding someone else's.
- `compileInputSchema` caches by schema object identity (WeakMap), so a schema is compiled once per discovery, not once per call.
- A schema that fails to compile (unresolvable `$ref`, unknown `$schema`) is forwarded **unvalidated**, with `unvalidatedReason` logged. The alternative — substituting `{type: 'object'}` — makes "we could not check" indistinguishable from "there are no constraints", and would also silently discard the schema the client was shown.
- Validation does not coerce. `{limit: "2"}` where the backend declared an integer is a client bug, and quietly fixing it produces a call the backend never expected.
- The advertised `outputSchema`, when present, is passed to `projectCallToolResult` so the SDK projects the result for the correct protocol era.
- **Accepted limit:** an uncompilable schema means no local validation for that tool. The backend is still the authority and will reject bad arguments; the gateway's rejection just arrives later.

## ADR-038 — The catalog is in-memory only
**Status:** Accepted  
`ToolCatalog` is derived state. There is no table, no migration, and no cache file.
- A persisted catalog outlives the connection it describes. It would either be served — lying about reachability — or distrusted on every read, which is the same as not storing it, plus a migration. Recovery already rewrites live connection state for exactly this reason (ADR-034); persisting the tools would recreate the problem one level up.
- A restart starts empty and rediscovery refills it. Discovery is idempotent, so "rebuild by asking again" is not just safe, it is the only description guaranteed to be current.
- The catalog is authoritative **within** its lifetime: routing reads it, but re-checks `isConnected` at call time rather than trusting the entry. A hint plus a fact beats two sources of truth.
- Conflict counts are computed at read time from the whole index rather than stored on each snapshot, because a conflict is a property of the catalog, not of one backend's discovery — and a stored count would go stale the moment a *different* backend connected or disconnected.
- **Accepted limit:** a process restart costs one `tools/list` per connected backend before their tools are callable. Acceptable for a local gateway with a handful of backends; a persisted snapshot with a validity check would be the upgrade path if that stops being true.

## ADR-039 — MCP authentication is per request; the hashing secret lives outside `Config`
**Status:** Accepted  
Phase 6 authenticates `/mcp` and authorizes nothing else. Three decisions make that safe to state.
- **Per request, no session binding.** Every exchange presents a bearer credential and is verified independently. `sessions` is untouched and no binding table was added. Cost: one indexed SQLite read per request. Benefit: revocation, a disabled agent, and a policy edit take effect on the next call instead of the next handshake, and no client-supplied id can become proof.
- **Credentials are HMAC-SHA-256, not SHA-256.** A plain digest would let anyone with a database copy verify guesses offline. The key (`CREDENTIAL_HASH_SECRET`) is a symmetric secret; `hash_key_id` records which key produced a digest so rotation needs no flag day.
- **The secret is read outside `Config`.** `apps/gateway/src/auth/credential-key.ts` and `apps/gateway/src/index.ts` read the environment directly. Putting it in `Config` would put it one serializer away from `redactConfig`, a config dump, and an API response. Production fails startup when it is missing; development starts with keys that issue nothing, so `/health` and the management API keep working while every `/mcp` request fails closed with the same 401. No ephemeral secret is generated — it would verify tokens only until the next restart.
- **Accepted limit:** anyone who can read the process environment can mint credentials. There is no automatic rehash-on-verify, so key rotation means adding a key id, revoking, and reissuing.

## ADR-040 — A denied tool call is byte-identical to a nonexistent tool
**Status:** Accepted  
Authorization runs **before** routing in `ToolRouter.call`, and both outcomes produce `-32602` with the message `Unknown tool`.
- Resolving first — backend lookup, reachability check, schema compile — would let a caller distinguish "exists but not yours" from "does not exist" by error code, error text, or timing. That turns the tool surface into a discovery oracle for the catalog it was denied.
- One catalog read does precede the decision: `resolveTarget` maps the public name to its backend because a `backend`-scoped rule cannot be evaluated without it. It is a lookup in the gateway's own in-memory index, performs no DNS, no socket, and no backend call, and yields the same result for a real and an invented name.
- No backend name, backend id, policy id, reason, or input schema is disclosed. `toProtocolError` special-cases `TOOL_NOT_FOUND` with a fixed string rather than echoing `AppError.message`, so a future message change cannot reintroduce the leak.
- The real reason is not lost: `access.denied` records it with the agent, credential, correlation id, and resolved ids. Internal truth, public uniformity.
- **Accepted limit:** because a denial for an existing name and one for an invented name take the same path, the gateway cannot avoid the catalog read; it only avoids disclosing anything that distinguishes the two responses.

## ADR-041 — Policy precedence is priority-first, then deny
**Status:** Accepted  
`evaluateAccess` sorts candidates by policy `priority` desc, then `deny` over `allow`, then policy id, then rule index, and denies when nothing matched.
- The spec's "explicit deny overrides all allow" is reconciled as: an operator's explicit priority ordering is authoritative, so a deny at a higher priority beats an allow; at *equal* priority the deny wins. Encoding deny-first globally would make priority decorative and let a catch-all deny in a low-priority policy silently disable a specific allow.
- The remaining tie-breaks exist so the outcome never depends on row order. Without them, two policies with the same priority and conflicting effects would resolve differently after a vacuum or a re-insert.
- System restrictions (agent disabled, backend disabled) are applied by `AuthorizationService` *before* the comparator and cannot be re-enabled by any rule, so "never" does not depend on an operator remembering to write a deny.
- **Accepted limit:** an operator can accidentally let an allow outrank a deny by giving it a higher priority. `GET /agents/:id/access` shows the winning policy and reason for every tool, which is the intended place to notice it.

## ADR-042 — `tools/list` and `tools/call` share one decision function
**Status:** Accepted  
`tools/list` filtering and `tools/call` enforcement both call `AuthorizationService` — the former through `visibleTools`, the latter through `authorize` in the router.
- Two implementations would drift: a tool could be hidden but callable, or visible and then rejected. The view and the boundary are one function read two ways.
- The `ToolCatalog` is still authoritative for *what exists*; `AuthorizationService` only answers *may this agent use it*. Keeping those separate is why the catalog needed no change to support filtering, and why a policy does not have to be re-validated when the catalog changes.
- Both are re-evaluated per request, so there is no cached decision to invalidate when a policy is edited.
- **Accepted limit:** every listed tool costs one evaluation per policy rule; fine for operator-sized policy sets, and it would need indexing before thousands of rules per agent.

## ADR-043 — Session binding is a stored, immutable row; serving is per era
**Status:** Accepted
Phase 7 binds a protocol session to an agent, but the binding is an additional check, never a substitute for authentication.
- **Two eras, verified not assumed.** Against the installed SDK (`2.4.0`), the 2026 era (`2026-07-28`) is per-request and issues no `mcp-session-id`, so there is nothing to bind. The 2025 era does issue one and is served through `WebStandardStreamableHTTPServerTransport` with `sessionIdGenerator` + `onsessioninitialized`/`onsessionclosed`. Serving both from a design that assumes one shape would have been a fiction.
- **Two request shapes take the sessionful leg:** a 2025 `initialize` (where a session is created) or a request already carrying `mcp-session-id`. Everything else stays on the SDK's stateless leg. The obvious alternative — routing *all* legacy traffic through the sessionful transport — was tried and rejected: it turned every sessionless one-shot `tools/list` into `400 Server not initialized`, breaking Phase 1–6 behaviour for clients that never wanted a session.
- **Status is stored; lifetimes are derived.** `status` is written explicitly because a terminal state (`terminated`, `invalidated`) is a decision, not a clock reading, and an operator's terminate must survive a restart. A lapsed `expires_at` or idle deadline is still derived in `sessionStatus()` and enforced **on the request path**, so a missed cleanup sweep cannot extend access. Cleanup only writes back what a request would already refuse.
- **Invariants live in the database.** A partial `UNIQUE` on `mcp_session_id`, a `BEFORE UPDATE` trigger freezing `id`/`agent_id`/`credential_id`/`mcp_session_id`/`created_at`, `sessions_no_reactivation`, and `sessions_terminal_is_complete` hold for every writer — including a second gateway process — which no in-memory lock could promise. Triggers rather than `CHECK` because SQLite cannot add a table-level constraint with `ALTER TABLE`.
- **The transport registry is process-local, and says so.** `McpSessionManager` is a `Map` of protocol id to transport. A session created by one process cannot be served by another; this is documented rather than papered over, and no Redis or shared lock was added for a single-process local gateway. Removing it would require a shared registry, not a bigger mutex.
- **Concurrency needs no mutex.** `better-sqlite3` is synchronous on one handle, and every session write carries its precondition in the `WHERE` (`status = 'active'`, `last_activity_at <= ?`), so decide-and-write is one statement. There is no window to lock and no lock to leak. `endWhere` uses `RETURNING` to release exactly the transports it ended.
- **Release is one-way through a callback.** `SessionService` takes `onEnded(sessions)`; `registry/` never imports `sessions/`. Every ending path — API terminate, revocation, rotation, disable, delete, cleanup, shutdown — funnels through it, so a dead session cannot leave an open server in memory.
- **Accepted limit:** a session id is useless without a bearer token, but the session refusals are deliberately uniform, so a client cannot tell *why* it was refused. That diagnosis lives in the `session.access.denied` audit row and the log, not on the wire (ADR-040's reasoning, applied to sessions).

## ADR-044 — Dashboard operator authentication is Phase 10, not a Phase 9 retrofit
**Status:** Accepted
Phase 9 delivers the dashboard foundation without an auth guard. Operator authentication is deferred to Phase 10.0 and must be built against a real identity model, not as a placeholder.

- **No identity exists to guard with.** The management API has never had an operator identity: it is unauthenticated and its boundary is loopback + Host/Origin + JSON content-type. A "guard" added now would have nothing to check a session against, so it could only be a flag that returns `true`. That is worse than no guard, because the UI would then label open operations as protected and teach an operator to trust a boundary that does not exist.
- **Placeholder auth is explicitly forbidden.** The project rules ban fake metrics, dummy records, and invented data; a dummy operator account or a hard-coded credential is the same class of problem, applied to security. It would also create a password-shaped artifact that must later be migrated or deleted.
- **Phase 9's own scope is the reason the deferral is safe.** Every module route except `/dashboard` is a placeholder with no mutation control, so there is no state-changing surface being left unguarded. The one exposed capability is a read of data that Phase 8 already serves to any loopback caller. Deferring does not widen access; it declines to *pretend* access is narrowed.
- **Two boundaries, not one ladder.** MCP agent credentials (Phase 6) and dashboard operator sessions answer different questions and must not share a table, a token format, or a verification function. An operator session must never authenticate an agent, and an agent bearer must never open the dashboard. Treating "we already did auth in Phase 6" as coverage for the dashboard would blur exactly the distinction that makes the agent boundary defensible.
- **The deferral is bounded and recorded, not open-ended.** Phase 10.0 is a prerequisite workstream with a required investigation list (single- vs multi-operator, identity model, mechanism, session lifecycle, cookies, login/logout, password vs external IdP, CSRF, authorization for sensitive operations, secret handling, local-only assumptions, recovery/bootstrap). No provider is chosen before that investigation; the choice gets its own ADR.
- **What still holds in the meantime.** Bind stays loopback. The browser still cannot reach the API directly — reads are server-side and client refresh goes through the same-origin allowlisted proxy. No tunnel, reverse proxy, or non-loopback bind. No "sign in", "account", or lock affordance appears in the UI while there is nothing behind it.
- **Accepted limit:** a local process or local user can do anything the API allows, exactly as before this phase. That is unchanged and documented in `SECURITY.md` §3.1 and §8.3 — the dashboard neither improves nor degrades it.

## ADR-045 — Phase 10.0: single local operator, opaque server-side session, gateway-enforced
**Status:** Accepted
Implements the boundary ADR-044 deferred. Scope is local-first: one operator account per gateway instance, session-based login, enforced in the gateway rather than in the Next.js app.

- **Identity model: one operator, no roles engine.** `admin_users` (already in 0001) holds `username`, `password_hash`, `enabled`, plus a `role` column that stays `owner`. Multi-operator, invitations, and role management are *not* built: they need an approval model, an audit story for privilege changes, and a UI that Phase 10 modules will need anyway. A single operator is the honest description of a local-first control plane, and the schema does not block adding peers later — `role` and the per-row timestamps already exist. Providing a role column is not the same as providing RBAC; nothing reads it.
- **Password hashing: scrypt from `node:crypto`.** No new dependency. Parameters are encoded *in the stored string* (`scrypt$N$r$p$salt$hash`) so a future cost bump verifies old hashes instead of locking the operator out. Verification uses `timingSafeEqual`. scrypt is memory-hard, which is the property that matters against GPU cracking of a human-chosen password; Argon2id would be marginally better but is not in the standard library, and adding a native module for a single-operator local tool is not a trade worth making.
- **No third-party identity provider.** An OIDC provider would mean a network dependency, an external account, and a redirect flow — for a gateway that must work offline on loopback. Passwords are the correct mechanism here. This decision is revisitable only if the product becomes multi-user and remote, which is explicitly out of scope.
- **Sessions are opaque, server-side, and stored in SQLite.** The cookie carries 256 bits of randomness; the server stores only an HMAC-SHA-256 digest (`operator_sessions.token_hash`) keyed by the same `CREDENTIAL_HASH_SECRET` already used for agent credentials, with its own key-id encoding. JWT was rejected: a stateless token cannot be revoked before expiry without a revocation list, and "logout must actually end access" is a requirement. Opaque + row lookup gives immediate revocation, single-session logout, and "disable the operator, end all their sessions" for free.
- **Session lifecycle mirrors the MCP session rules that already exist.** Idle timeout (default 30 min) and absolute lifetime (default 12 h), both enforced on read from the two stored instants, so a missed sweep cannot extend access. Rotation happens at login: a new session id is minted on every successful authentication, and the pre-login session (if any) is revoked, which is what makes session fixation impossible. Expired rows are kept with a reason for audit.
- **Cookie: `HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` conditional.** The dashboard is served over plain HTTP on loopback, so `Secure` would make the cookie unreachable and produce a login that silently never works. Therefore `Secure` is set when the request arrived over HTTPS (forwarded proto is *not* trusted; the decision uses the explicit `OPERATOR_COOKIE_SECURE` setting, default off, documented as "turn on only behind TLS"). `SameSite=Strict` is the CSRF primary defence; a double-submit token is the second.
- **CSRF: same-site cookie + explicit token, not Origin alone.** `SameSite=Strict` stops cross-site sends, but same-site ≠ same-origin on loopback (another port is same-site), and a compromised sibling origin would pass. Every state-changing request therefore requires an `X-CSRF-Token` header matching a value bound to the session. The token is *derived*, not stored separately: `HMAC-SHA-256(key = the cookie value, message = "operator-csrf-v1")` (`csrfFor` in `apps/gateway/src/registry/operator-service.ts`), so it cannot drift from the session, needs no extra column, and cannot be computed without the cookie — which is exactly what a cross-site request lacks. Comparison is `timingSafeEqual`. This is a second lock, not a defence against XSS: nothing cookie-derived is.
- **Enforcement lives in the gateway, not in Next.js.** This is the decision that matters most. The management API is reachable directly on `127.0.0.1:8787`; a Next.js middleware guard would be cosmetic, because any local process could still call the API. The gateway therefore verifies the operator session itself on every `/api/v1` request. A BFF-only design was rejected for exactly this reason — it protects the browser path and leaves the documented API path open.
- **The browser obtains a session by talking to the dashboard, which talks to the gateway.** Next.js route handlers own the login form POST, forward credentials to the gateway over loopback, and re-issue the gateway's `Set-Cookie` on the dashboard origin. The gateway is the only place a password is verified and the only place a session is minted. The browser never holds a gateway credential, and no internals are proxied: the allowlist still governs which reads exist.
- **Health and readiness stay unauthenticated.** `/health` and `/ready` are operational probes whose purpose dies if they require a session; neither returns sensitive data (counts and check states only). Everything under `/api/v1` requires an operator session except the auth endpoints themselves.
- **Bootstrap is a CLI command, not a default account.** `pnpm operator:create` reads the password from stdin or a TTY prompt with confirmation, never from an argument (which lands in shell history and `ps`). It refuses to run when an operator already exists, so it cannot silently reset a password. There is no default password, no generated password in the logs, and an unconfigured instance answers login with a clear "no operator is configured" rather than a crash loop.
- **Login failure is uniform.** Unknown operator, disabled operator, locked operator, and wrong password all produce one message and take comparable time (a dummy scrypt verify runs when no row matches, so response timing cannot enumerate usernames). Lockout is 5 failures → 15 minutes, stored on the row as `locked_until` so it survives a restart, and it is deliberately not permanent: a local operator with no recovery UI must not be able to lock themselves out forever.
- **Audit events are new enum values, not free-form strings.** `operator.login.succeeded`, `operator.login.failed`, `operator.logout`, `operator.session.revoked`, `operator.session.expired`, `operator.created`, `operator.disabled`, `operator.password_changed`. Actor type `admin`, actor id = the operator id for successes and `undefined` for failures (naming a username in an audit row would record an attempted identity). No password, no cookie value, and no token digest is ever written.
- **MCP authentication is untouched.** Different table, different digest key-id namespace, different verifier, different middleware, different cookie/header. An operator session is never accepted on `/mcp`, and an agent bearer is never accepted on `/api/v1`. ADR-039 and ADR-043 remain in force verbatim.
- **Accepted limits, stated plainly.** Loopback-only means any *local user* who can reach the socket can attempt a login; this raises the bar from "no authentication" to "must guess a password", not to "remote-hardened". `SameSite=Strict` means a deep link from an external site lands on the login page rather than the target. There is no rate limit per IP beyond per-account lockout, so a distributed guess against many usernames is not slowed — with one operator account, "many usernames" is not a practical surface. No TLS is terminated here, so cookies can be read by anything that can read loopback traffic; that is the documented cost of local HTTP.

## ADR-046 — Phase 11: hand-rolled in-memory metrics registry, closed-enum labels, two exports behind the operator boundary
**Status:** Accepted
The requirement is counts in memory and a way to read them out; the decision is what *not* to import, what a label may never be, and which boundary the export sits behind.

- **No Prometheus/OpenTelemetry/Redis dependency.** prom-client or the OTel SDK would import a second pipeline — collectors, exporters, registries, config — for a single loopback process whose entire need is "increment a number, render it on request". `apps/gateway/src/monitoring/metrics.ts` is ~500 lines of counter/gauge/histogram primitives instead. The escape hatch is the Prometheus text 0.0.4 format itself: a future migration to prom-client can render the same series names and no scraper notices.
- **In memory, resets on restart — documented, not apologized for.** The registry is rates and ratios, never a record. The durable per-event trail already exists (`activity_events`, `audit_events`); a time-series store would be a third store of the same facts, kept without a concrete consumer. The dashboard card says "since process start · resets on restart", which is the honesty mechanism.
- **Labels are closed enums, by construction.** Route class, MCP method, outcome, transport, stable error code (`^[A-Z][A-Z_]{0,63}$`), HTTP status (`^\d{3}$`). A tool name, agent id, username, or anything a caller chose is **never** a label: an unbounded label is a cardinality bomb and a disclosure in one — `umg_tool_calls_total{tool="payments.refund"}` would turn a metrics export into a topology map. Violations are dropped and counted in `umg_metrics_dropped_total`, so under-counting is visible; per-metric series caps bound memory; no metric call can throw into a request path.
- **One module-level singleton, not constructor threading.** Every writer imports `metrics` directly. This is a deliberate exception to the dependency-injection style of the registry layer, for the same reason the logger is: the aggregate must be reachable from *any* layer — domain, adapter, transport — and constructor threading exists precisely to prevent that reachability. Nothing in the registry reads configuration or storage, so the singleton has no hidden state to inject.
- **Two exports, one boundary.** Root `GET /metrics` (Prometheus text) and `GET /api/v1/monitoring/metrics` (JSON) render the same numbers. The text export sits behind the **same operator session cookie and loopback check as `/api/v1`** — an unauthenticated metrics port is the classic leak, and "loopback only" is not an access control (ADR-045's accepted limits). Mounted only when an operator row exists at assembly time, the same restart-after-`operator:create` semantics every configured feature has; a fresh install answers `404` rather than exposing an empty registry without auth.
- **`initialize` counts at session creation.** The SDK's `Server` registers its own initialize handler in its constructor — there is no public hook — so the gateway counts `umg_mcp_method_total{method="initialize"}` at `onsessioninitialized`: a session exists if and only if initialize succeeded, which is the one outcome this process owns. The help text says this rather than implying a refused initialize was observed. SDK-answered pings and notifications are not counted at all.
- **MCP-handler refusals count `outcome: failure`, all of them.** Denials must stay indistinguishable on the wire (ADR-039, and Phase 6's `Unknown tool` uniformity) — a metrics label the *caller* can read would leak the reason. The denial split therefore lives in the router's counters (`umg_authz_denied_total`, `umg_mcp_session_denied_total`), which only an operator reads.
- **Errors split by category.** Client-category refusals (bad `limit`, unknown tool) feed `umg_errors_total{code,component}` only — they are business as usual, high-volume, and would drown the diagnostics ring. Internal-category and unhandled errors additionally enter a bounded 20-entry ring of `{code, component, at, requestId}` — never messages, stacks, or driver text, because the ring's job is to be safe to paste into a bug report.
- **Accepted limits, stated plainly.** DB operation durations are uninstrumented: better-sqlite3 is synchronous, so a "duration" would measure a function call, not a query — recording it would be fabricated precision. A scrape renders before counting itself, so one scrape's own request appears in the next; scrapers must not read the self-row. Restart history is nowhere; anything needing history must read the activity table, not the registry.

## ADR-047 — Phase 11: AsyncLocalStorage correlation, validated-never-trusted inbound ids, activity-row join
**Status:** Accepted
Correlation ids are an operator convenience for joining log lines to rows; the decision keeps them from becoming a trust input, a global, or a second identity system.

- **One middleware, first on the outer app, before any guard.** A request refused by loopback rejection or a guard is still a request the process did work for, and its refusal is exactly what an operator most needs to correlate. `requestCorrelation` generates or echoes `X-Request-Id` and runs the whole chain inside `AsyncLocalStorage`.
- **`X-Correlation-Id` is validated, never trusted.** Inbound must match `^[A-Za-z0-9._-]{1,64}$` or it is replaced — no rejection, no trust. An unsanitized header is a log-injection primitive: newlines, ANSI escapes, and forged JSON fields would flow into pino's structured stream. The id's entire authority is "group my log lines"; it never authenticates, never authorizes, never keys a cache.
- **ALS, not a global, not a threaded parameter.** A global `currentRequestId` breaks under concurrency — two interleaved requests would cross-contaminate every log line, the bug redaction exists to prevent, not introduce. Threading a parameter through every signature from middleware to repository to audit write is the alternative, and it costs a touched signature per call site forever for zero behavior. ALS gives both: any log site reads `correlationLogFields()` with no signature change, and concurrent requests are isolated by construction. `apps/gateway/tests/correlation.test.ts` pins the isolation across awaits.
- **Existing explicit request ids stay explicit.** JSON-RPC ids and operator action ids have their own semantics already; this phase adds only `correlationId` via the context. Where a handler already logs `requestId` from its own source, that line keeps its meaning — the two id systems are not merged.
- **The join lands on activity, not audit.** Migration `0007` adds nullable `activity_events.correlation_id`: one client task may span several gateway requests, which is exactly what a correlation id groups, and activity answers "what did the gateway do". Audit answers "who changed what" and already persists the per-exchange `request_id`; a caller-supplied trace id in the security trail would let the *subject* of an audit row choose part of its key. Nullable, no default, no index: nothing queries by correlation id yet, and a write-path index with no reader is pure amplification — add one when a consumer exists.
- **Structured logging redacts at the serializer, not at call sites.** Pino's redaction list covers `authorization`, `cookie`, and the `*.token|credential|credentialHash|password|secret|apiKey` families, so a stray field cannot leak a verifier even if a future call site adds one by accident — redaction that depends on every author remembering is not redaction. Tool arguments and upstream responses are never logged at all; `describeErrorForLog` keeps messages but drops payload objects.

## ADR-048 — Phase 12: two tool source types, one catalog, identity domains that never merge
**Status:** Accepted
The gateway gains a second way for a tool to exist — a managed integration — without gaining a second catalog, a second authorization model, or a second identity system. The decision is what stays singular, and what the distinction is allowed to cost.

- **`sourceType` is a closed two-value enum; `sourceId` is its pair, not an optional extra.** `mcp_backend` (the original and still primary source, `sourceId` = backend id) and `managed_integration` (`sourceId` = gateway-generated connection id). The pair is stable from the moment a tool enters the catalog, so a stored client config — a public tool name — never changes meaning underneath its owner. A third value requires editing this enum, not a config file.
- **Three identity domains, deliberately non-interchangeable.** Agents call, operators administer, connections represent an operator's instance of a registered provider. A *provider* is code registration (what the connector is); a *connection* is a row (whose credentials, whose tools, which status). The id spaces are disjoint by construction: `ProviderRegistry` ids never enter the catalog, connection ids are UUIDs minted at creation, and a backend rule naming a connection id is rejected at policy creation (see ADR-052) — the domains do not merge at any layer that validates.
- **One catalog, one keyspace, composite snapshot keys.** Sources are keyed `"<sourceType>:<sourceId>"`, so the same id held by a backend and a connection is two sources, not a collision. Public tool names remain `<sourceId>__<tool>` for both types — the deterministic namespacing path is reused, not forked, and **no existing MCP public name changes**: `sourceId` equals the old `backendId` on the MCP path, character for character.
- **`backendId` survives only where it is true.** The `CatalogTool` union keeps `backendId` on `mcp_backend` rows (equal to `sourceId`, so every pre-Phase-12 reader keeps working) and fabricates nothing on managed rows — an absent field is honest; a lying `backendId` would survive into logs, authorization queries, and conflict claimants. Conflict claimants name their source with the same honesty: MCP claimants carry `backendId`, managed claimants don't.
- **A cross-source name collision withholds both claimants and says why.** Two sources normalizing to one public name (`a b` / `a_b`) conflict exactly like two backends always have: neither is routable, `resolve` answers `conflict`, and the claimants list lets an operator see which source to rename. No silent priority between source types — priority would be a policy decision wearing a routing costume.
- **The activity row names its source once, structurally.** Migration `0008` adds nullable `activity_events.connection_id`, and the activity schema itself refuses a row naming both a `backendId` and a `connectionId` — a writer bug fails at the read boundary instead of poisoning every consumer. Audit gains the `connection` target type; the new audit actions are closed-enum values, not free-form strings (ADR-051).
- **Accepted limits, stated plainly.** Managed tools have no discovery report surface: `catalog.reports()` is MCP-only, because a report describes an MCP handshake and fabricating one for a connector would be theater. `toolTarget()` maps `sourceId` into the existing `backendId` rule field internally — the field name is historical, the value is the source id, and renaming a rule field is a versioned policy-schema change held for a phase that needs it.

## ADR-049 — Phase 12: one execution seam, connectors as bounded guests
**Status:** Accepted
A managed call must be authorized, observed, and audited exactly like an MCP call, and a connector must never be trusted the way a gateway component is trusted. The decision is a single dispatch seam and a contract that keeps connectors outside every trust boundary.

- **One branch after authorization, not a second pipeline.** `ToolRouter.call()` keeps its one shape: resolve, authorize, record, dispatch. Dispatch is `if (tool.sourceType === 'managed_integration') callManaged(...)` — one seam — and the MCP-only helpers are narrowed to the MCP variant of the union, so the compiler enforces the seam instead of the review. Nothing about the MCP path was rewritten to make room for the new one.
- **Authorization happens once, before the seam, with the existing evaluator.** A denied caller of a managed tool gets the same uniform answer as a denied caller of an MCP tool, and the connector records zero executions — pinned by a test that counts them. No code path authorizes *after* dispatch, and none passes the connection's credentials through authorization: the execution principal is the agent, always.
- **The connector context is a whitelist, not a convenience bag.** Exactly `{ connectionId, metadata, resolveCredential, signal, timeoutMs }` — no store handle, no services, no credential value eagerly materialized, no agent or operator identity. `resolveCredential(credentialId)` is the only way to a secret, and it is backend-only, audited on every call (ADR-051). A test pins the key set; a field added to the context is a security review, not a refactor.
- **Timeout and cancellation are enforced by the gateway, not requested of the connector.** `withCancellation` wraps every connector operation with the context's `timeoutMs` and `AbortSignal`, so a connector cannot forget the budget, and a cancelled call surfaces as `BACKEND_TIMEOUT` — the same code the MCP path uses, because from a client's perspective the transport is not the distinction.
- **Connector errors are normalized at the seam onto the existing codes.** `timeout → BACKEND_TIMEOUT`, `unreachable → BACKEND_UNAVAILABLE`, `invalid_request → VALIDATION_ERROR`, `provider_error → BACKEND_CONNECTION_ERROR`, `reauthorization_required → TOOL_UNAVAILABLE`. The client sees a fixed message; the connector's own words go to `details`, which never leaves the process — a provider message can name URLs, scopes, or internal paths. Renaming public error codes is a versioned API change and is held.
- **`reauthorization_required` is a state change, not an error report.** The call closes with `TOOL_UNAVAILABLE`, the connection flips status, its tools leave the catalog in the same instant, and the state is terminal until an operator acts (ADR-050). Execution fails closed on the way *into* the state and stays closed after — the router never re-drives it.
- **Fail closed is the default, at every gate.** No `integrations` runtime wired → `TOOL_UNAVAILABLE`, never an MCP fallback behind the seam. A stale in-memory catalog entry (row says `disconnected`, catalog still lists the tool) → the runtime's `dispatchable()` gate refuses before the connector runs. A tool-level `isError` result passes through as a routed result — a failed tool is a completed round trip, not a transport failure — recorded as `outcome: failure` without an exception.
- **Accepted limits, stated plainly.** Discovery and execution are separated but both synchronous from the caller's chair: `connect()` awaits a full discovery round trip, so a slow provider slows the operator action, not the request path. There is no connector sandbox: a connector is code compiled into the gateway, which is exactly why the contract is narrow and why the registry is code, not a plugin loader (ADR-050).

## ADR-050 — Phase 12: registry as code, lifecycle as data, zero production providers
**Status:** Accepted
Phase 12 defines the shape of managed integrations without shipping one real provider. The decision keeps that honesty structural: the registry ships empty, the lifecycle is a table, and nothing about either can be widened by configuration.

- **The provider registry is a module constant, and it ships empty.** `providerRegistry` is imported, never constructed from configuration, never loaded from disk: no dynamic loading, no marketplace, no plugin directory, no `providers.json`. A provider exists when a developer writes a registration into code and ships a release — which means "zero production providers" is a fact about the build, not a promise about runtime. Tests build their own registry instances; production code cannot inject one through configuration.
- **Registration validates twice and fails closed both times.** The zod schema bounds every field; `register()` then cross-checks the declared capabilities against the connector's actual methods — declaring `execution` without `executeTool` is `CONFIGURATION_ERROR` at registration, not a latent `undefined is not a function` at call time. A duplicate id is `RESOURCE_CONFLICT` and never overwrites the first entry: the registry has no "last write wins" anywhere in it.
- **Seven statuses, and the legal edges are data.** `CONNECTION_TRANSITIONS` is a list of pairs, same declaration style as the backend runtime states, so a test enumerates all 49 pairs instead of sampling a few. Two rules carry the weight: **an operator can disable a connection from any non-terminal status** (including `connecting` — "wait for it to finish" is not a safety property), and **`disabled` is the only terminal status**. `error` and `reauthorization_required` exit only through an explicit operator `connect` (after re-storing a credential) or `disabled` — the router can drive a connection *into* trouble but never *out* of it; recovery is operator work.
- **A transition that is not in the table is refused, not repaired.** `transition()` throws `RESOURCE_CONFLICT` naming both statuses; the row keeps its current status. The service has no fallback path, no "close enough" repair, and the DB CHECK constraint agrees with the table — a hand-edited status fails at the write, and any other hand-edited corruption fails at the read boundary as `DATABASE_ERROR`.
- **Withdrawal is synchronous with the state change.** `disconnect`, `disable`, and `remove` write the status and remove the catalog source in the same call — there is no window where a tool is listed and unroutable, or routable and unlisted. `remove` also deletes the credential rows via the migration's FK cascade, so a secret cannot outlive its connection by accident of order.
- **Multiple connections per provider are first-class.** One provider, two orgs, two connection rows, two tool namespaces; deleting one never touches the other's catalog entries — pinned by a test that does exactly that and then calls through the survivor.
- **Accepted limits, stated plainly.** Connections are created with a caller-supplied UUID id (`CreateConnectionInput`), which exists so tests and future operator tooling can be deterministic — the id is validated, not generated, and a duplicate id is an integrity refusal, not a retry. There is no connection-scoped rate limiting, retry budget, or health sweep this phase: a failing connector fails the call and (for auth failures) flips the status; anything periodic is Phase 13+ with a consumer named.

## ADR-051 — Phase 12: envelope vault for integration credentials — references in the database, values nowhere at rest
**Status:** Accepted
A managed connection may hold a credential the provider will accept. The decision is that the database stores a *reference* to an envelope, the envelope stores ciphertext and nothing else, and the master key never lives in the database it protects.

- **AES-256-GCM, twice, per record.** Each `seal()` mints a random 32-byte DEK, seals the payload with it (fresh nonce, AAD binding the key id), and wraps the DEK with the master key (fresh nonce, AAD binding the key id). Every record has its own key and nonces; one compromised envelope is one compromised record, and GCM's tag makes tampering a detectable failure, not a quiet one.
- **The wrap tag is its own envelope field.** `wrappedDek` is pure ciphertext and `wrapTag` is the tag — no length arithmetic, no "last 16 bytes are the tag" convention. The first version of the code stripped the tag at seal and re-derived it from the stripped ciphertext at unseal, an envelope no correct key could ever open; the vault test suite caught it before anything depended on it, and the envelope schema now makes the mistake unrepresentable. `v` versions the whole shape so a future format change is a migration, not a guess.
- **The master key comes from the environment, only.** `INTEGRATION_MASTER_KEY` (base64, 32 bytes), optional `INTEGRATION_MASTER_KEY_PREVIOUS` for rotation. No config file, no database row, no default: the key that decrypts the database must not be *in* the database, and a default key would be a lock painted on. The key id is digest-derived (never the key bytes), printed in `details` on mismatch so an operator can see which key sealed a record the process no longer holds.
- **Lazy fail-closed, never degraded.** A missing key does not block startup — the gateway comes up, serves MCP, and lists integrations; the first credential operation refuses with `CONFIGURATION_ERROR`. No plaintext fallback, no weaker algorithm "for now", no warning-then-write: the write that would create an unencrypted secret simply cannot happen, and the connection row keeps `credentialId: null`.
- **References ≠ values, at every boundary.** The connection row stores `credentialId` — a UUID, zod-enforced, so a pasted `sk-live-...` string is a validation error, not a stored secret. Audit actions `integration.credential.sealed` / `.resolved` record the reference and the actor, never the value; the resolver is exposed only through the connector context (ADR-049) and every resolution is audited. No endpoint returns a credential value; the API surface documents none; a test scans every database file byte-for-byte for the secret after a round trip and finds none.
- **Rotation is the previous slot, not a re-encryption campaign.** Sealing always uses the active key; unsealing tries active then previous. Records sealed under an old key stay readable until they are re-stored, which is an operator action per credential — automatic background re-encryption would need a queue, a lock, and a failure story, for a credential count that is currently zero in production.
- **Accepted limits, stated plainly.** The DEK lives in memory only during a seal or an unseal — there is no key cache to attack, and also no mlock: a memory-scraping local attacker defeats this vault, as they defeat every secret in a loopback process. Envelope integrity is per-record GCM; there is no HSM, no KMS, no external sealing service, because each would add a network dependency to a gateway whose principle is that it runs alone on one machine.

## ADR-052 — Phase 12: participation without drift — policy, database, API, observability
**Status:** Accepted
The hard rule of this phase: a managed tool must participate in everything (authorization, metrics, audit, operator API) without any of those systems learning a second way to work. Five surfaces, one decision each.

- **Policy: the existing evaluator stays the source of truth, unchanged.** `AuthorizationService` maps `tool.sourceId` into the evaluator's existing `backendId` query field — for MCP the value is literally unchanged, for managed tools the field carries the connection id under its historical name, and the evaluator, its schema, and its migration story are untouched. A `backend`-scoped rule naming a connection id is **rejected at policy creation** (`validateRules` checks the backends table): a connection is not a backend, and letting the id ride the field for *queries* while refusing it for *grants* is the difference between reuse and domain merger. Managed tools are granted through tool-scoped rules and wildcards, exactly like MCP tools.
- **Database: migration `0008` is additive-only, and the upgrade is tested on real bytes.** Two new tables (`integration_connections`, `integration_credentials` with FK cascade and a status CHECK) plus nullable `activity_events.connection_id`; no existing column changes type, drops, or narrows. The test builds a genuine Phase 11 database (migrations 0001–0007, rows written with Phase 11-shaped SQL), opens it under Phase 12, and asserts every row survived, the new tables exist empty, and reopening is idempotent.
- **API: read-only, operator-authed, honestly empty.** `GET /api/v1/integrations/providers` and `/connections` sit behind the same operator session as every `/api/v1` route; unauthenticated callers get `401` on both. Production answers `{ "data": [] }` because the registry ships empty — that is the truth, and the empty state is rendered rather than padded. There is **no write endpoint and no dashboard UI**: with zero registered providers a connection form would be a form over nothing, and Phase 13 mounts the write API on the same service. No credential-value endpoint exists at all (ADR-051), and the OpenAPI document — kept in parity in both directions by test — contains exactly the two read paths.
- **Observability: reuse the existing series, never fork them.** A managed call is a `tools.call` activity row and a `umg_tool_calls_total` increment — one pipeline, no `managed_tool_calls_total`, because a second series would be a second place a dashboard could drift. The correlation context gains `connectionId` alongside `backendId` (mutually exclusive on the row, enforced structurally); `integration.connection.*` and `integration.credential.*` join the audit actions as closed-enum values — the actions have no DB CHECK, consistent with every prior phase: the enum lives in zod at the boundary, and the boundary is where corruption fails.
- **Accepted limits, stated plainly.** `providers`/`connections` list everything with no pagination, no filters, and no per-connection tool listing — the honest production count is zero, and shape follows the count. Audit metadata for credential events carries the credential reference; it deliberately does not carry a digest of the value, because a digest of a low-entropy token is a lookup table, and Phase 12 does not need one. The dashboard shows nothing new: no integrations page exists to show, and an empty page is not a milestone.

## ADR-053 — Phase 13: GitHub as the first registered provider, exercised end to end
**Status:** Accepted
Phase 12 built the managed-integration machinery and deliberately shipped none of it populated. Phase 13's rule is the mirror of that honesty: register exactly one real provider, keep it read-only, and drive every Phase 12 surface — vault, catalog, policy, execution, audit, metrics — through it. If the machinery only works with fixtures, this phase is the one that finds out.

- **The registry gains its first code entry: GitHub, read-only, fine-grained PAT.** `githubRegistration` is written into the same `REGISTRATIONS` constant ADR-050 froze — still no configuration, no plugin loader, no marketplace. The auth surface is a fine-grained personal access token asking for Metadata, Issues and Pull requests (read); the gateway requests no write permission and offers no tool that could exercise one. The connector is a factory (`createGitHubConnector({ fetchImpl?, sleep? })`) so tests inject a fixture `fetch` and **no test in the repository dials `api.github.com`**.
- **The HTTP client is provider-owned, and its discipline is code, not comment.** Fixed origin `https://api.github.com`, HTTPS only, no caller-suppliable URL; the headers are `Authorization: Bearer`, `X-GitHub-Api-Version: 2026-03-10`, `Accept: application/vnd.github+json`, `User-Agent: universal-mcp-gateway`. The mapping is closed: `401` and permission-`403` are `reauthorization_required`; rate-limit `403` (`X-RateLimit-Remaining: 0`) is distinguished from permission `403`; other `4xx` are `invalid_request`; `5xx` and malformed bodies are `provider_error`; network failures are `unreachable`. Retry is bounded to **one**, only when the provider sends `Retry-After ≤ 5s`; everything else fails fast. Provider prose never crosses the boundary — the connector vocabulary is the only text an operator or an agent can see.
- **Six tools, normalized or refused.** `list_repositories`, `get_repository`, `list_issues`, `get_issue`, `list_pull_requests`, `get_pull_request` — strict zod inputs, bounded pagination, fixed endpoint paths, timeouts with cancellation, and identity fields required by the normalizers (a shape failure is a failure, never a `?? ''` fallback that would mint a half-true record). Only `list_repositories` accepts empty args. Namespacing and publication ride ADR-048 unchanged: `<connectionId>__<tool>` on `publicName`, discovery and execution through the same catalog and the same authorization as every other tool.
- **The operator write API mounts on the Phase 12 service, with `test` as data and `enable` as the only door to `connected`.** `create` leaves the row `pending` — storing a token proves nothing. `POST …/credential` is write-only (ADR-051): the token goes in, a vault reference comes back, a replacement deletes the previous envelope in the same transaction. `test` runs the handshake — for GitHub, one authenticated `GET /user` — and **moves nothing**: both outcomes are `200` data (`{ ok: true }` or `{ ok: false, kind, message }`), so a refused token cannot masquerade as a server error. `enable` is the single path that stamps `validatedAt` (migration `0009`, nullable, honestly `null` until the first proof) and publishes tools; it is also the only exit from `disabled` and the only reconnect — nothing reconnects automatically. `disable`, `disconnect` and `DELETE` are explicit, audited as `integration.connection.updated`/`.deleted` with a status detail, and the credential route stays POST-only: no read surface for a secret the gateway refuses to store in any readable form. All of it sits behind the same operator session, CSRF check and origin discipline as every prior write route; the OpenAPI document keeps path parity by test.
- **The dashboard gets the three screens the flow needs, and no fourth.** `/dashboard/integrations` (list, honest empty state naming the registered provider), `/new` (create — the step that takes no secret), and `/[connectionId]` (the credential panel, the lifecycle actions with their consequences stated before the click, the published tools). The PAT exists in one input's state and nowhere else: the field is cleared when the request answers, success or failure; it is `type="password"`, `autoComplete="off"`, never rendered back, never written to storage, cookie, or URL. Destructive steps — disable, disconnect, delete, replace-token — ask first through `AlertDialog`, and delete names the hard-delete cascade. The write proxy's allowlist gains the integrations paths as anchored UUID expressions, test-enumerated for refusals like every other module.
- **Accepted limits, stated plainly.** Read-only, one provider, no OAuth, no GitHub Apps, no webhooks, no enterprise hosts — each is a separate decision with its own blast radius, and none is needed to prove the architecture. The token's reach is whatever the PAT grants; the dashboard does not pretend to enumerate it (`validatedAt` says when it was proved, not what it can see). Rate-limit and retry budgets are per-request, not per-process: there is no token bucket in the gateway yet, and adding one is a Phase 14+ question that only matters once agents call these tools without an operator in the loop.

## ADR-054 — Phase 15: integration platform hardening (audit-first, no widening)
**Status:** Accepted
Phase 13 proved the platform with one real provider; Phase 15 proves it against itself. The phase began with a full audit of the as-built system — every integration source file, the routing seam, the vault, the API, the dashboard, all seven test files — and shipped only what the audit found: four code-level gaps and the tests that pin them. No new provider, no new tool, no new surface, no second vault, no dynamic anything. `docs/INTEGRATION_PLATFORM.md` is the durable output for the developer who adds the second provider; this ADR records why the four changes are the right shape.

- **`enable` on a live connection is now the refresh: `connected → connecting` is a legal edge.** Before Phase 15 the only way to re-discover a connected row was disable/enable — disconnect in between, tools withdrawn, a round trip no operator would guess. The refresh keeps the old tool set listed but undispatchable for the flight (`connecting` is not callable), replaces the snapshot wholesale on success, and reports the diff like a first connect. The edge joins the transition table the 49-pair test enumerates, and a new test pins `connected`'s five exits exactly: refresh, disconnect, error, reauthorization, disable.
- **A failed refresh withdraws the stale tool set — the documented consistency policy.** An `error` or `reauthorization_required` row never lists tools, matching the backend-side precedent that an unreachable source is unlisted, not listed-and-failing. Before the refresh edge existed this was unreachable (only never-published rows could fail); making refresh possible made the policy necessary, and the same withdrawal now covers both paths. Failed connect/refresh attempts also write an audit row with `result: 'failure'` — the attempt is operator history, with the landing status and connector kind in metadata, never a message or value.
- **Concurrent lifecycle is ownership, not locking: the row must still be `connecting` after the flight.** Discovery is a network await, and `connect()`'s success continuation used to publish unconditionally — a mid-flight delete published a ghost catalog, a mid-flight disconnect resurrected what the operator just took down. The continuation now re-reads the row: gone → `404`, nothing published; moved on → `409`, the racing action's outcome stands. A second simultaneous `connect` was already impossible (no `connecting → connecting` edge → `409`); now it is tested. All pinned by `apps/gateway/tests/integrations-concurrency.test.ts` against the production service through a gated fixture connector — no sleeps, no real network, deterministic flight control.
- **The GitHub client's redirect boundary is enforced by the request, not by undici's courtesy.** The client always promised no redirects to another host; `redirect: 'error'` makes the fetch itself refuse any hop, so the promise holds even if the platform's cross-origin header-stripping ever changes. One line in the client, one assertion in the fixture recorder.
- **`umg_tool_calls_total` gains a closed two-value `source_type` label — one series, still no fork.** ADR-048 refused a second counter for managed calls; the label answers "how many of each kind" at zero cardinality risk because the enum is closed in the spec and out-of-enum values drop (counted, never silent). Per-*provider* figures stay where they already are — activity and audit rows name the connection, the connection names its provider — because a `provider` label would couple the metrics path to registry strings that are developer-chosen. Denials keep `outcome` only: they are counted before the catalog read, and a denied caller costs no extra work by design. The dashboard's Telemetry card splits its tool-call rows into two exact reads per outcome rather than summing the closed pair — every rendered number stays a series the registry actually keeps.
- **The dashboard's live row says "Refresh"** (same `enable` route, announcement reporting the added/removed diff) — without it the new backend capability would be invisible to the only surface operators use. The three-screen shape is unchanged; no new route, no new proxy entry.
- **Accepted limits, stated plainly.** The connections list stays unpaginated — an operator's count is small, and the response shape is a published contract. `connect()` stays synchronous from the operator's chair (ADR-049's accepted limit): a slow provider slows the `enable` request, never the MCP request path. Multi-connection isolation was already structural (namespaced public names, per-connection snapshots, scoped credential resolution refusing foreign references — now tested at the service level); Phase 15 added no isolation code because the audit found none missing. The provider checklist in `docs/INTEGRATION_PLATFORM.md` is a floor, not a gate bypass: it cannot substitute for the security review or for explicit user approval of the next provider.

## ADR-055 — Phase 16: Notion as the second registered provider, read-only
**Status:** Accepted
Phase 15 hardened the platform against itself; Phase 16 proves the hardened shape generalizes. The audit-first rule held (the ten-item report preceded any code), and the phase's success criterion was structural: a provider with a different credential model, a different pagination model (opaque cursors, not numbered pages), a different content model (a block tree, not flat records), and a post-2025 database/data-source split — landing with **zero provider-specific logic outside `apps/gateway/src/integrations/notion/`**. The vault, lifecycle, catalog, authorization, execution pipeline, operator API, dashboard screens, audit, and metrics are reused byte-for-byte; the proof is the diff: three new files under `notion/`, one registry entry, prose, docs, and tests.

- **The registry gains its second code entry: Notion, read-only, internal connection token.** `notionRegistration` joins `githubRegistration` in the same frozen `REGISTRATIONS` constant — still no configuration, no plugins, no marketplace. Least privilege is one checkbox in Notion's portal (Read content); the gateway registers no write tool and no write path exists in the connector. The credential rides the identical write-only vault envelope (ADR-051), and the connection-scoped resolver already refused foreign references — now proven against two live-notion connections in one catalog.
- **The client mirrors the GitHub discipline with Notion's own facts.** Fixed origin `https://api.notion.com`, HTTPS, `redirect: 'error'`, no caller-suppliable URL, no logger in the module. Every request pins `Notion-Version: 2026-03-11` (the current official version) beside `Authorization: Bearer`. Rate limits (180/min per connection, 600 Business/Enterprise, plus per-workspace) are honored with the same bounded policy: **one retry, only when `Retry-After ≤ 5 s`**, otherwise a fast failure carrying the reset fact. Notion's error prose never crosses the boundary; the five-kind vocabulary is the only text an operator sees.
- **Six tools onto six current endpoints; the data-source model matched.** `search` → `POST /v1/search`; `get_page` → `GET /v1/pages/{id}`; `get_block` → `GET /v1/blocks/{id}`; `list_block_children` → `GET /v1/blocks/{id}/children`; `get_database` → `GET /v1/databases/{id}` (the post-split retrieve, whose `data_sources` array the tool surfaces for chaining); `query_data_source` → `POST /v1/data_sources/{id}/query`. The phase's mandated set fit the current API exactly, so no read-only alternative tool was needed. Inputs are strict (UUID-pattern ids, `page_size` ≤ 100, opaque cursors bounds-checked and echoed verbatim, `filter` ≤ 50 keys, `sorts` ≤ 10) and outputs are closed zod `.strict()` shapes: unknown response fields ignored, unknown and future block types **recorded with their type and an honest `text: null`** — never silently dropped — and properties rendered best-effort with the type always stated.
- **Pagination is caller-driven by construction.** One page per call returning `{ items, hasMore, nextCursor }`; the caller passes `nextCursor` back as `start_cursor`. The gateway never loops, never accumulates, never auto-fetches children or embedded URLs — so the "bounded traversal" requirement is satisfied by having no traversal at all.
- **The handshake proves authenticity, and the docs say so.** `GET /v1/users/me` (get-self) is the connect-time proof; Notion has **no capability-listing endpoint**, so breadth cannot be verified at connect time — a connection missing Read content connects and then fails closed per request with `403`. `validatedAt` records the proof; `docs/providers/NOTION.md` §11 records the limitation rather than papering over it, and the bot user's workspace name is deliberately never stored.
- **Everything else is the platform's, unchanged — and now double-covered.** No Notion management route exists (the generic lifecycle API is the whole surface); the dashboard's one provider-specific sentence is the credential panel's Notion hint (capability, portal link, the sharing-pages explanation a fresh connection needs); the registry-pin, provider-listing, and security-state tests now state the two-provider truth; and the router-level suite drives the real registration with two Notion connections, two agents, and a GitHub connection publishing alongside — eighteen tools, zero collisions, each call proven to carry its own connection's sealed token. **Live Notion account validation: NOT PERFORMED — requires separate user approval.** No test dials `api.notion.com`; the six GitHub tools and every prior suite stayed green through the full gate.
- **Accepted limits, stated plainly.** No OAuth or public connections, no personal access tokens, no write tools, no webhooks, no arbitrary URL fetching, no capability handshake, no per-process rate budget — each is a separate future decision. A third provider follows the same checklist (`docs/INTEGRATION_PLATFORM.md` §12) and the same explicit-approval gate; nothing about this phase makes the next one easier to skip.

## ADR-056 — Phase 17: Slack as the third registered provider, read-only
**Status:** Accepted
Phase 17 is the third pass over the checklist (`docs/INTEGRATION_PLATFORM.md` §12), and its success criterion is again structural: a provider whose failure model differs from both predecessors — **Slack answers application failures as HTTP 200 with `{ok: false, error: "<code>"}`** — landing with **zero provider-specific logic outside `apps/gateway/src/integrations/slack/`**. The audit-first rule held (the ten-item report plus official method research preceded any code); the vault, lifecycle, catalog, authorization, execution pipeline, operator API, dashboard screens, audit, and metrics are reused byte-for-byte; the proof is the diff: three new files under `slack/`, one registry entry, prose, docs, and tests.

- **The registry gains its third code entry: Slack, read-only, manually supplied bot token.** `slackRegistration` joins `githubRegistration` and `notionRegistration` in the same frozen `REGISTRATIONS` constant. There is **no OAuth flow in the gateway**: the operator pastes a Bot User OAuth Token (`xoxb-`) through the write-only vault path; expiry/revocation surfaces as `reauthorization_required`, and no refresh infrastructure exists or is needed for a static token. Least privilege is nine read scopes — `channels/groups/im/mpim` `:read` + `:history`, `users:read` — each justified by exactly one tool; never a write, a manage, a commands, or an email scope. The connector refuses a non-bot token (`xoxp-`, `xapp-`) **before any request leaves the gateway**, because `auth.test` alone would happily pass a token that then misses every scope.
- **The client encodes Slack's two-envelope rule.** Every answer is read on both halves — transport status **and** app-level `ok` — so a 200 with `ok: false` is the failure it says it is and a non-200 is still a transport failure. The stable `error` code is a closed vocabulary and is quoted inside the gateway's own message; no other failure-body field (`detail`, `needed`, warnings) ever crosses the connector boundary. Fixed origin `https://slack.com/api`, HTTPS, `redirect: 'error'`, no caller-suppliable URL, no logger in the module, no version header and no `User-Agent` (Slack asks for neither), and the same bounded rate-limit policy: **one retry, only when `Retry-After ≤ 5 s`**, otherwise a fast failure carrying the reset fact.
- **Five tools onto five current methods; `search.messages` is documented out, not approximated.** `list_conversations` → `conversations.list`; `get_conversation_info` → `conversations.info`; `get_conversation_history` → `conversations.history`; `get_thread_replies` → `conversations.replies`; `get_user_info` → `users.info`. The audit's research finding is stated rather than worked around: **`search.messages` is a user-token-only method** (`search:read` is a user scope; bot tokens are not supported), so the gateway does not implement it and invents no synthetic replacement — retrieval stays listing- and history-shaped, and `docs/providers/SLACK.md` §17 records the exclusion with the reference.
- **Slack identity is string identity.** A `ts` value is `epoch.microseconds` — an id whose fractional digits address a thread — so timestamps are carried as **exact strings, never float-parsed**, re-checked by pattern at the connector; a number is refused at the schema. The one deliberate conversion goes the other way (conversation `created` epoch-seconds → readable ISO 8601), because that field is metadata, not an id. Unknown message subtypes are recorded, not dropped; reactions and reply-user lists are simply not read; file references are text at most. Pagination keeps the Phase 16 contract — one page per call, `{items, hasMore, nextCursor}`, cursor opaque and echoed verbatim — with Slack's own dialect handled: `conversations.list` has no `has_more` and answers an **empty-string cursor** at the end, so one rule (a present cursor means more) covers both dialects, and `limit` is a deliberate gateway bound (≤ 200) below Slack's documented maxima.
- **The handshake proves authenticity, and the docs say so — again.** `POST auth.test` (the one scope-less method) is the connect-time proof of token, workspace, and bot identity; Slack offers **no endpoint that lists a token's scopes**, so breadth is enforced per request — a token missing `channels:history` connects and then fails closed with `missing_scope` → `reauthorization_required`. The identity the handshake returns is deliberately never stored, so two Slack workspaces are two fully independent rows — the router-level suite drives two Slack connections with two agents plus Notion and GitHub connections publishing alongside: twenty-two tools, zero collisions, each call proven to carry its own connection's sealed token.
- **Everything else is the platform's, unchanged — and now triple-covered.** No Slack management route exists (the generic lifecycle API is the whole surface); the dashboard's one provider-specific sentence is the credential panel's Slack hint (the `xoxb-` shape, the nine read scopes, the `api.slack.com/apps` link, and the private-channel invite explanation a fresh connection needs); the registry-pin, provider-listing, and security-state tests now state the three-provider truth. **Live Slack workspace validation: NOT PERFORMED — requires separate user approval.** No test dials `slack.com`; every prior suite stayed green through the full gate.
- **Accepted limits, stated plainly.** No OAuth or app-installation flows, no write tools, no Socket Mode (outbound HTTPS is the only Slack surface), no webhooks, no file downloads, no DM-listing guarantees beyond membership, no per-process rate budget — each is a separate future decision. A fourth provider follows the same checklist and the same explicit-approval gate; nothing about this phase makes the next one easier to skip.
